# Launcher plan

Objective: write down, as the product's direction, a world-class plan in which the hub is a launcher that installs and updates its components independently (the hub itself, the server, and modules such as the Word add-in), with the two accepted non-goals. Branch: `feature/launcher-plan` from `dev`. Delivery: `ask-on-risk`. Passive documentation: structural readback, no test runner.

## Specs

- **S1** — Direction (user, verbatim): "Yo creo que podemos apuntar grande desde el inicio. Yo creo que podemos hacerle un hub que permita descargar las actualizaciones del addon. También es uno de los motivos por los que se puso al backend también su propio tag de versión." and "Quiero que seas ambicioso, que crees un plan que lleve esto a First World Class." The launcher model (HoYoPlay-like, user's analogy) is the product direction: the hub is installed once; the hub, the server and every module are versioned, released and updated independently. No hybrid fallback is the goal; the installer may carry nothing but the hub.
- **S2** — Accepted non-goals (user: "los últimos dos márcalos ya como aceptados que no se van a hacer"): (a) buying an Authenticode code-signing certificate to avoid SmartScreen on the hub installer; (b) Microsoft Marketplace or centralized deployment to load the add-in without the trigger window. Recorded as accepted, with their consequence (SmartScreen warning on first install; the trigger window stays).
- **S3** — "todo lo demás es perfectamente lograble con desarrollo propio": the plan covers, as own development, the design decisions below (D1–D12), each with its milestone, exit criteria and the failure cases it must survive.
- **S4** — Written where it governs: `docs/roadmap.md` restructured around the launcher milestones (keeping the reached milestones, the M3 analysis-reliability items and the M5 product-readiness items, renumbered), `docs/architecture.md` gains a "Target architecture: component delivery" section (current vs target), and a decision record `docs/adr/0001-component-delivery.md` (context, decision, alternatives rejected — bundled-only, hybrid —, consequences).

### Design decisions (parent's design; writers phrase them, never drop or invent)

- **D1 Components.** Three kinds, each its own repo/tag: `hub` (Electron shell, tags `hub-v*`), `server` (the backend bundle, tags `server-v*`, run by the hub in its `utilityProcess`), `module` (each with an `id` and a `kind`; first kind `office-addin`, the Word add-in; the kind field leaves room for others without designing them now).
- **D2 Release artifact.** Every server and module release publishes a zip plus a `component.json`: `id`, `kind`, `version`, `channel`, `sha256`, `size`, `requires` (`hub` range, and for modules the server `api` range such as `^1`), `provides` (server: API versions served, SQLite `schemaVersion`), release notes URL. Published as GitHub Release assets of the component's own repo.
- **D3 Own signing (no CA).** ed25519 detached signatures over `component.json` (which pins the zip's sha256). The private key lives only in CI secrets; the hub embeds a keyring of public keys with key ids, so keys can rotate; a revoked key id list ships in the catalog.
- **D4 Signed catalog (TUF-lite).** The hub repo publishes `catalog.json`, signed, listing per component and channel the current version and its artifact URLs. It carries a monotonically increasing `serial` and an `expires` date, so the hub rejects rollback (an older serial) and freeze (an expired catalog) attacks. Fields for staged rollout (`rolloutPercent`) and for blocking a bad version.
- **D5 Update engine (hub main process).** Checks on start and periodically; downloads into staging with resume; verifies size, sha256 and signature; resolves compatibility (hub range, server API vs each module's required range) and refuses an update set that would break another component; installs atomically into `%LOCALAPPDATA%/stylistic-hub/components/<id>/<version>/` with a `current` pointer; keeps the previous version; never extracts outside its target (zip-slip guard).
- **D6 Health checks and automatic rollback.** After switching a server version the hub waits for `/api/v1/status`; after switching a module it checks its manifest and task pane are served. Failure, or a crash loop detected by `supervisor.ts`, rolls back to the previous version and records why; the bad version is not retried until a newer one appears.
- **D7 Server data safety.** Migrations are forward-only and expand/contract: a release never drops what the previous release reads. The hub copies the SQLite file before a server version with a higher `schemaVersion` starts; a rollback restores that copy. Downgrade below the database's `schemaVersion` is refused unless a backup exists.
- **D8 Module serving and Word.** Each module is served at `/m/<id>/` on the hub origin, with the versioned asset URLs and `Cache-Control` the hub already applies (`bef61c1`). Word re-registration happens only when a module's manifest identity changes; a new version takes effect on the next task pane open, and the task pane can ask the hub (`/api/v1/modules`) whether a newer version is installed and offer a reload.
- **D9 Channels and rollout.** `stable` (from `main`) and `beta` (from `dev`, prereleases) per component, chosen in the hub UI; staged rollout by hashing a random install id against `rolloutPercent`; a version can be pulled from the catalog.
- **D10 Hub self-update.** electron-updater from the hub's GitHub Releases, unsigned (S2 accepted), with the same channels.
- **D11 Library UI.** A HoYoPlay-like library screen: one card per component with installed/available version, channel, progress, release notes, and install, update, repair, uninstall, roll back; update history visible; first run downloads the server and the modules the user picks.
- **D12 Pipeline and contracts.** Each repo's GitHub Actions: `check`, build, pack, sign, publish release assets; the hub repo's catalog updates through a reviewed PR. Contracts enforced in CI: the module contract (today's `docs/addin-contract.md`, generalized) runs in the module's CI; the API's OpenAPI document is diffed against the last release and a breaking change fails unless the API major version changes (v1 additive only; v2 served alongside). Developer overrides: `--server <dir>`, `--module <id>=<dir>`, a local catalog file, and a dev signing key.
- **Cross-cutting quality bar.** Fault-injection tests for the update engine (killed mid-install, corrupt download, bad signature, expired or older catalog, failing health check → rollback); local structured logs, update history and an exportable diagnostics bundle; module-scoped tokens instead of one shared hub token (a module only reaches the API scopes it declares).

- **L7** (2026-10-17): Judgment Day round 1 on `87f2248`: no CRITICAL from either judge (protocol verdict APPROVED); both confirmed six design gaps (WARNING/SUGGESTION), corrected on the user's instruction to iterate. Parent decisions for the correction (R1–R9):
  - **R1 Catalog trust and freshness (A2, A3, B5).** Two key roles: an offline **root key** (kept off CI, used rarely) signs a `keys.json` listing the online keys and their roles; an online **catalog key** in CI signs `catalog.json`; online **component keys** sign `component.json`. A scheduled CI job re-signs the catalog (new `serial`, `expires` = +14 days) daily even with no change, so it never lapses unattended; a lapse of more than 14 days only blocks updates. An expired or older catalog never stops installed components: they keep running (offline too); the hub shows the reason and retries. The last-seen `serial` lives in the hub's `userData`; a reinstall that loses it trusts the first valid, unexpired catalog (stated as accepted trust-on-first-use).
  - **R2 Rotation and revocation (A1, B6).** Rotating online keys needs no new hub: the root key signs a new `keys.json`. Only a root rotation ships in a hub, with the next root public key embedded one release ahead. Revocation is enforced at every catalog check, not only at install: an installed version covered only by a revoked key is disabled and replaced by the catalog's current version.
  - **R3 Hub self-update is signed by us (A1, B2).** "Unsigned" in D10 means no Authenticode only. The hub is a component in the signed catalog like the others: the update engine downloads the hub installer named there and verifies its sha512 and our signature before electron-updater (generic provider, pointed at the verified file) installs it. This also removes the dependency on GitHub's "latest release" of a repo that publishes `server-v*` too.
  - **R4 Repositories (B1).** Two repos today: `stylistic-hub` publishes the `hub` and `server` streams (tags `hub-v*`, `server-v*`), `stylistic-addon` publishes the `office-addin` module stream; a future module may live in its own repo. Release streams, not repos, are per component.
  - **R5 Database rollback (A4, B3, B4).** Each server release declares `schemaVersion` and `minReaderSchema` (the lowest schema it can still read). The server opens a database whose schema is newer than its own when its version is at least that database's `minReaderSchema` (a change to `database.ts`, which today refuses any newer schema). An expand step keeps `minReaderSchema`, so rolling back opens the same database with no restore and no lost writes; only a contract step raises it, and only then is the backup restored on rollback (writes since the upgrade are lost, and the hub says so). The backup is taken with `VACUUM INTO` (consistent while the server runs in WAL mode) into the `userData` backups folder before the new server starts; a restore stops the server and removes stale `-wal`/`-shm` files. A downgrade is refused when the older server is below the database's `minReaderSchema` and no backup of a readable schema exists.
  - **R6 Word registration and migration (A5, B9).** The registered manifest lives at a stable path (`components/<id>/manifest.xml`, rewritten on each version switch), never under a versioned folder. The hub re-registers whenever that manifest's content hash changes (new ribbon commands, a new source location), not only its identity. Cutover from 0.0.1: the first launcher hub re-registers the add-in at `/m/<id>/`, removes the root-URL entry and migrates the bundled server's database in place; users on 0.0.1 install that hub once by hand (0.0.1 has no self-update). To make every later cutover automatic, hub self-update (D10) moves into the update-engine milestone.
  - **R7 Supervisor and first install (A6).** Crash-loop detection is new work in `supervisor.ts` (today: backoff forever): N exits within a window before a stable run marks the version failed. A failed first install with no previous version leaves the component "not installed" with the reason and a retry, never a restart loop.
  - **R8 Binding and extraction (A9, B7).** Before anything is extracted the engine checks that the signed `component.json` matches the catalog entry (`id`, `kind`, `version`, `channel`, `sha256`) and that `id` and `version` match strict patterns; extraction rejects absolute paths, `..`, symlinks and Windows reserved names, and stops at an uncompressed size cap declared in `component.json`.
  - **R9 Smaller corrections.** Fixture-based compatibility tests in the update-engine milestone before modules ship (A7, B10); `%LOCALAPPDATA%` for components is deliberate (large binaries off the roaming profile) while state, backups and the last-seen serial stay in `userData` (A8); the Sigstore note rests on complexity, not on an online verifier (B8); T1 commit recorded (B11).
